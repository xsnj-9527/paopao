# 泡泡 Agent 评测：指标与归因定义

> 配套：`cases/`（用例）、`reports/latest.md`（最近一次报告）
> runner 在 `../agent-core/src/test/kotlin/com/deepseekbuddy/agent/eval/`，一条命令跑：`cd ../agent-core && ./gradlew runEval`

---

## 一、为什么要冻结时间和注入存储

用例里每条都写死了 `now`（如 `2026-09-14T22:30:00+08:00`）。runner 把时钟、便签存储、记忆存储、提醒调度器**全部换成注入实现**：

| 注入项 | 真实环境 | 评测环境 |
|---|---|---|
| 时钟 | `ZonedDateTime.now()` | 用例里的 `now`，冻结 |
| 便签 / 记忆 | Room（`AppDao`） | 内存 List |
| 提醒 | AlarmManager + 通知 | 记录调用参数 |

**结果**：同一份用例在任何机器、任何时刻跑，结论一致。这是「指标能当回归基线」的前提——否则「明天早上七点半」这类用例今天过、明天挂，指标就没有意义。

## 二、五个指标

| 指标 | 定义 | 分母 | 为什么是它 |
|---|---|---|---|
| **任务完成率** | 工具序列、参数、回答、工具执行四项全部达标 | 全部用例 | 唯一能对外讲的数字。面试官问「你的 Agent 好用吗」，答这个 |
| **工具选择正确率** | 实际工具序列与期望**完全一致**（有序、数量相等），且没调用 `forbidden` 里的工具 | 全部用例 | 与「任务完成率」分开，是为了区分**选错工具**和**参数算错**——两者改法完全不同 |
| **参数正确率** | 用例声明的参数断言**全部**通过 | **声明过参数断言的用例** | 分母刻意不含没写断言的用例，否则加一堆「只测工具名」的用例就能把指标刷高 |
| **平均轮次** | 每次任务平均请求模型几次 | 全部用例 | 成本与延迟的代理指标。轮次涨了说明工具返回的信息不够用 |
| **平均估算 token** | 输入上下文 + 工具 schema，按 **2 字符/token** 估算 | 全部用例 | 与 App 侧 `TokenBudget.estimate` 同一口径，可直接和线上预算对照 |

> **口径声明**：`平均估算 token` 是**估算**，不是 API 返回的真实 usage——`DeepSeekClient` 目前没有解析 `usage` 字段。做压缩策略对比时看**相对变化**是可靠的，别把它当账单数字。

## 三、失败归因：六个格子

失败用例会被自动分到六类之一。**分类的价值在于「改哪里」完全不同**——把工具 bug 当成模型不会用，就会去改提示词，越改越糟。

| 归因 | 判据 | 该改哪里 |
|---|---|---|
| **模型问题 · 工具选择** | 调了 `forbidden` 的工具，或工具序列不符（该调没调 / 调错 / 数量不对） | 改系统提示词、改工具 `description`，或换模型。**不要动用例。** |
| **模型问题 · 参数编造/算错** | 工具选对了，但参数断言不通过 | 先看参数描述是否歧义；描述没问题才归给模型能力 |
| **模型问题 · 未完成任务** | 工具与参数都对，但回答不达标 | 检查收尾提示与 `MAX_TOOL_ITERATIONS` |
| **工具问题** | 任一工具调用 `success == false` | 工具返回了失败，或实现与 `description` 不符。**改工具。** |
| **用例问题** | 用例本身不可判定 | 修评测集 |
| **评测问题** | 匹配器比需求更死 | 修匹配器 |

**判定顺序**（写在 `Evaluator.classify` 里，顺序本身是设计）：

```
工具执行失败？  → 工具问题
  ↓ 否
运行期异常且没调过工具？ → 用例问题
  ↓ 否
工具选错 / 调了禁止的？  → 模型问题 · 工具选择
  ↓ 否
参数不对？              → 模型问题 · 参数
  ↓ 否
回答不达标？            → 模型问题 · 未完成
```

先查工具、再查模型——否则工具 bug 会被误算成模型不会用。

## 四、三种运行模式

| 模式 | 命令 | 特点 | 用途 |
|---|---|---|---|
| **空跑** | `./gradlew runEval` | 不调模型，全部如实判失败 | 验证评测流水线本身没坏 |
| **回放** | `./gradlew runEval --args="--replay ../evals/replay/v1.json"` | **确定性** | 当回归基线；改提示词/工具 schema 后看指标怎么动 |
| **真实** | `DEEPSEEK_API_KEY=sk-xxx ./gradlew runEval --args="--live --record ../evals/replay/v1.json"` | 有随机性、花钱 | 反映真实水平；`--record` 把回复录下来供回放 |

**为什么非要「回放」这一档**：真实 API 的 temperature 默认 **1.2**，同一份用例今天 82%、明天 76% 是常态。想判断「我这次改提示词到底有没有变好」，就必须让模型这一侧固定不动——**只让我的改动成为唯一变量**。这正是四份 JD 里反复点名的「控制变量」。

## 五、回归对比

```bash
# 1) 先存一份基线
cd ../agent-core
./gradlew runEval --args="--replay ../evals/replay/v1.json"
cp ../evals/reports/latest.json ../evals/reports/baseline.json

# 2) 改动（改 prompt / 改工具 description / 加压缩策略），再跑
./gradlew runEval --args="--replay ../evals/replay/v1.json --baseline ../evals/reports/baseline.json"
```

输出会给出五个指标的**前后对比**，以及：

- **新通过**：上次挂、这次过的用例（改动有效的证据）
- **新失败**：上次过、这次挂的用例（回归！）
- 新增 / 移除的用例

## 六、第一次真实运行暴露的三个评测缺陷（2026-09-13 修正）

第一次拿真实模型跑（`--live`）跑出 72.7%，但归因表一看就不对劲：**8 条失败里 5 条是同一个模式** ——
模型在设提醒前先调了一次 `get_time`。

去读代码才发现：**App 的系统提示词里根本没有注入当前时间**，反而明确写着
「问时间时调用 `get_time`，**以工具返回为准**」，而 `get_time` 的 description 是「**不要自己推算**」。
所以要算「明天早上七点半」的绝对时间戳，**先查当前时间是唯一正确的做法**。

**是我的用例错了，不是模型错了。** 三处修正：

| # | 缺陷 | 修法 |
|---|---|---|
| 1 | 工具序列写死「严格相等」，把合理的准备性调用判成选错工具 | 用例新增 `allowExtra`：期望序列按**子序列**匹配，多出来的调用只允许是声明过的准备性调用 |
| 2 | 「只要工具返回失败就归因成工具问题」—— 但 `create_reminder` 拒绝一个已过去的时间是**正确行为** | `ToolResult` 新增 `FailureKind`：参数校验失败归模型，工具内部异常才归工具 |
| 3 | `rem-03` 的期望与它自己的 rationale 自相矛盾（rationale 说「追问也可接受」，期望却只认 `create_reminder`） | 用例新增 `alternatives`：可接受的替代结果序列；走替代序列时主期望的参数断言不再适用 |

**修正前后（同一批模型回复，用回放重算，没有重跑 API）：**

| 指标 | 初版（严格序列） | 修正后 |
|---|---|---|
| 任务完成率 | 72.7% | **87.9%** |
| 工具选择正确率 | 72.7% | 87.9% |
| 参数正确率 | 90.5% | **100.0%** |
| 通过条数 | 24/33 | **29/33** |

**回归对比确认这不是放水**：`新通过 4 条：rem-01, rem-02, rem-04, rem-08；新失败 0 条` ——
修正只纠正了误判，没有让任何一条本该失败的用例蒙混过关。

修正后剩下的 4 条**都是真失败**：漏设提醒（multi-01）、把时间算成过去后重试（multi-04）、
无关多调一次 `remember_fact`（note-02）、凭空回答而不查时间（time-03）。

> 这一段本身就是「**判断某个机制是模型能力问题、Harness 设计问题、数据问题，还是评测问题**」
> 的实例 —— 而那正是月之暗面 Harness PE 岗点名要求的能力。

## 七、评测器自己也要被评测

`EvaluatorSelfTest` 用**手写模型脚本**构造 6 种已知情形，钉死指标数值与归因分类：

| 用例 | 构造情形 | 期望归因 |
|---|---|---|
| A-pass | 正确调用 `get_time` | 无（通过） |
| B-no-tool | 该调工具却直接编答案 | 模型问题 · 工具选择 |
| C-forbidden | 纯计算题却去查时间 | 模型问题 · 工具选择 |
| D-wrong-arg | 提醒时间算错（07:30 写成 09:00） | 模型问题 · 参数 |
| E-tool-defect | 提醒时间已过去，`ReminderTool` 拒绝执行 | **工具问题** |
| F-incomplete | 工具调对了，回答缺关键词 | 模型问题 · 未完成 |

> 这套自测**已经抓到过一个真 bug**：`E` 原先被判成**通过**——因为评测器只比对了工具序列，没检查工具是否真的执行成功。「工具名对 = 任务做成」是个很容易犯的错，而且它会系统性地虚高所有指标。
